# 覚醒モード（KENGOODメソッド）

複雑なタスクの実作業前に実行する 6 ステップの覚醒手順。
完了後に「覚醒ブリーフィング」を提示してから実作業に入る。

## 発動しない条件

目的と完了条件が明確で、低リスクかつ局所的であり、複数段階の調査・設計・
外部連携を必要としない単純なタスクには使わない。直接実行する。
判定が微妙な場合は **失敗コストと不可逆性** を基準にし、高ければ発動する。

---

## 覚醒手順（6ステップ）

### Step 1: 目的と完了条件の言語化

- このタスクの目的を 1〜2 文で言語化する
- 「何ができたら完了か」を検証可能な形で定義する
- 目的や完了条件が曖昧なままなら、推測で進めずユーザーに質問する

### Step 2: コンテキスト装填

- `mistakes.md`（反省ノート）を読み込み、今回のタスクに適用されるルールを列挙する
- Vault がある場合は `wiki/INDEX.md`（第2の脳）を確認し、関連トピックを実作業に持ち込む
- プロジェクトの CLAUDE.md・既存コード・既存ドキュメントのうち、影響範囲にあるものを確認する

### Step 3: 前提の検証

- 重要な前提を列挙し、「確認済みの事実」と「未確認の推測」に分類する
- 不明点を事実のように扱わない。検証可能なものはツールで検証する
- 検証できない前提は、ブリーフィングに前提として明記する

### Step 4: リスク・盲点・代替案

- 失敗した場合のコストと不可逆性を評価する
- 盲点、リスク、機会、反対意見、代替案を必要な範囲で挙げる
- 不可逆な操作（削除・上書き・外部送信・公開）が含まれる場合は、実行前にユーザー確認を挟む計画にする

### Step 5: 実行計画

- 「今やること」と「今はやらないこと」を分けて明示する
- 複数段階のタスクは手順に分解する（大規模ならプランモードの使用を検討）
- 助言だけで終わらせない。安全かつ権限内で、実務成果物と検証まで進める計画にする

### Step 6: リソース設定

- **思考深度**: 難しい設計判断・デバッグには拡張思考を深く使う。単純な手作業には使わない
- **モデル**: 品質が問われる計画・レビューは上位モデル、機械的な実行・確認は軽量モデルが適する（変更はユーザーの明示的な依頼がある場合のみ）
- **サブエージェント**: 独立した調査・作業が複数並列できる場合のみ検討。トークン消費が大きいため、並列化の効果が見込める時に限る

## 覚醒ブリーフィング（出力フォーマット）

覚醒手順の完了後、実作業に入る前に以下を簡潔に提示する:

```
## 覚醒ブリーフィング

- **目的**: [1〜2文]
- **完了条件**: [検証可能な形で]
- **適用ルール**: [mistakes.md から該当するもの。なければ「該当なし」]
- **前提**: [確認済み / 未確認を区別して]
- **リスク**: [失敗コスト・不可逆性・盲点]
- **今やること**: [手順]
- **今はやらないこと**: [スコープ外の明示]
- **検証方法**: [完了をどう確かめるか]
```

ブリーフィングは長くしない。各項目 1〜3 行。提示したら実作業を開始する。

---

## 品質基準（複雑タスク共通）

- 結論を先に示し、事実・根拠・論理を優先する
- 「最適解」を保証せず、利用可能な情報・権限・時間の範囲で最も根拠の強い解を目指す
- タスク完了時、ミスがあれば反省ノートのルール化 3 条件に照らして `mistakes.md` への追記を検討する

## 優先順位

ユーザーの明示的な指示、適用されるプロジェクト固有の指示（CLAUDE.md）を本スキルより優先する。
