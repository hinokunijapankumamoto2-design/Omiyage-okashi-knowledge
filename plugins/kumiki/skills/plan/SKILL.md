# 木取り — 切る前に、どう切るかを決める

**In one line:** decide what would prove you wrong, before you go looking for what proves you right.

木取りは、板のどこをどう使うか決める工程。切ってしまってからは戻せない。
調査も同じで、集め始めてから問いを変えると、集めたものが全部無駄になる。

## この型を使う条件

- 依頼が「〜について調べて」「〜を検討して」の形で、**完了条件が書かれていない**
- 論点が3つ以上ある、または利害が対立している
- 一度出した結論を後で説明する必要がある

逆に、答えが1つに定まる事実確認には使わない。過剰な段取りは、それ自体が浪費。

## 手順

### 1. 依頼を「決定」に翻訳する

「調べて」で止めない。**誰が、何を、いつ決めるのか**まで書く。

```
依頼:   お土産菓子市場を調査して
翻訳:   2027年春の新商品を「駅ナカ主体」で出すか「空港主体」で出すか、
        商品企画部が10月末までに決める。その判断材料を揃える。
```

翻訳できないときは、ここでユーザーに聞く。**この一手を省くと、後の全工程が
的外れになる。** 聞くのはこの1回だけにする。

### 2. 反証可能な主張に割る

答えではなく、**真偽が判定できる文**を3〜6個立てる。

```
✗ 「駅ナカ市場は有望である」          … 判定できない
✓ 「駅ナカの土産菓子売上は2024→2026で年平均5%以上伸びている」
✓ 「空港チャネルの粗利率は駅ナカより5pt以上高い」
✓ 「単価1,500円超の商品は駅ナカで棚を取れていない」
```

### 3. 各主張に「これが出たら否定」を書く

主張ごとに、**それを潰す証拠**を先に決める。これを書かないと、都合のいい
情報だけが集まる。

```
主張: 駅ナカ売上は年平均5%以上伸びている
否定: 主要3社のIR資料で駅ナカ部門が2年連続前年割れ
出典候補: 各社決算説明資料、JR系商業施設の売場面積推移
```

### 4. コストを見積もる

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/kumiki.py" thrift plan ./knowledge --budget 30000
```

既存資料で足りるか、`/kumiki:gather` が要るかがここで決まる。

### 5. 進め方を1枚に書く

`knowledge/decisions/YYYY-MM-DD-<テーマ>.md` に残す。

```markdown
---
title: <決定の名前>
date: 2026-08-29
status: open        # open / decided / superseded
decides: 誰が何をいつ
---

## 主張と反証条件
| # | 主張 | 否定する証拠 | 出典候補 | 状態 |
|---|---|---|---|---|

## 完了条件
全主張が confirmed / refuted / insufficient のいずれかに確定していること。

## やらないこと
（範囲外を明示する。ここが空欄の計画は必ず膨らむ）
```

## 深く考えるとき（ultrathink 相当）

「もっと深く」と言われたら、思考量を増やすのではなく**検証の粒度を上げる**。

1. **前提を1つずつ外す。** 各主張について「これが成り立たない世界」を1文で
   書く。書けない前提は、まだ前提として認識できていない。
2. **反対側の最強の論を書く。** 弱い反論を潰しても何も分からない。自分の結論を
   最もよく壊す議論を、こちらから書く。
3. **二次効果まで見る。** 「駅ナカに寄せる」→ 棚は取れる → 単価が下がる →
   粗利率が落ちる → 空港向け高単価品の開発余力が減る。1手で止めない。
4. **数字の出所を1段深く辿る。** 引用の引用は使わない。一次資料に当たれない
   数値は「未確認」と明記する。

## ゲート

次工程に進む前に、この3つが揃っていること。揃っていなければ戻る。

- [ ] 誰が何をいつ決めるかが1文で書ける
- [ ] 主張それぞれに「否定する証拠」が書かれている
- [ ] やらないことが書かれている

揃ったら `/kumiki:gather`（材料がない）または `/kumiki:weave`（材料がある）へ。
