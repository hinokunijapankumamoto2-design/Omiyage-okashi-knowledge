# AI 動画制作スタジオ アーキテクチャ

## 中心にある設計判断: 実行層を 2 つに分ける

このスタジオの構成を決めているのは、**すべてのツールが同じ方法では呼べない**という制約である。

| 実行層 | 呼び出し元 | 対象ツール |
|---|---|---|
| **script 層** | Node プロセス（`src/cli.ts`） | codex exec / HyperFrames / Remotion / ffmpeg |
| **agent 層** | Claude 本体 | Kling MCP / Figma MCP / video-use スキル |

MCP ツールと Claude Code スキルは、Node の子プロセスからは呼べない。呼べるのは Claude 自身だけである。
この非対称性を無視して「全部を 1 本のスクリプトで回す」設計にすると、必ず途中で破綻する。

そこでオーケストレータは、agent 層のステップに到達すると**停止し、`project.json` の `agentTask` に
「Claude が何をすべきか」を書き出す**。Claude がそれを読んで MCP を実行し、結果を書き戻してから
`run` を再開すると、続きから進む。

```
studio run <id>
   │
   ├─ script 層のステップ → その場で実行して次へ
   │
   └─ agent 層のステップ → agentTask を書いて停止（exit code 2）
                              │
                              ├─ Claude が MCP / スキルを実行
                              ├─ 結果を assets/ に保存し project.json に登録
                              └─ studio run <id> で再開
```

この往復を明示的な成果物にしてあるので、「いまどこまで進んで、次に誰が何をするのか」が
プロジェクト単位で常に追跡できる。中断しても状態は `project.json` に残る。

## 8 工程と担当

| # | 工程 | 担当 | 層 | 実装 |
|---|---|---|---|---|
| 1 | 企画 | Claude + Figma MCP | agent | `steps/01-plan.ts` |
| 2 | 台本 | Claude | agent | `steps/02-script.ts` |
| 3 | 素材生成 | codex exec + GPT Image 2 | script | `steps/03-image.ts` |
| 4 | モーション制作 | HyperFrames / Kling | 両方 | `steps/04-motion.ts` |
| 5 | 実写編集 | video-use | agent | `steps/05-capture.ts` |
| 6 | 字幕 | スタジオ内製（SRT 生成） | script | `steps/06-subtitle.ts` |
| 7 | 画面合成 | Remotion | script | `steps/07-compose.ts` |
| 8 | 最終レンダリング | Remotion | script | `steps/08-render.ts` |

## 工程4 がハイブリッドである理由

モーション制作には性質の違う 2 種類がある。

- **HyperFrames**（`heygen-com/hyperframes`）— HTML/CSS を決定論的に MP4 / 透過 WebM にする。
  テキストアニメ・図解・ロワーサードのように**作り込みと再現性が要るもの**を担当。
  同じ入力なら毎回同じ絵が出るので、修正のたびに絵が変わってしまう事故が起きない。
- **Kling** — 静止画に生成的な動きを付ける。実写風のカメラワークや被写体の動きを担当。
  MCP 経由なので agent 層。

判定は `motionPrompt` の文面ではなく、**そのショットが静止画素材を持つか**で行う。
静止画がある = その絵を動かしたい → Kling。無い = ゼロから作る → HyperFrames。

## HyperFrames と video-use は別物

当初の想定と異なり、この 2 つは同一ではない。video-use の README 自身が HyperFrames を
外部プロダクトとして参照している。

- **video-use**（`browser-use/video-use`）— 実写素材の編集スキル。フィラー語除去、カラーグレード、
  単語レベル ASR に基づくカット、字幕焼き込み。**HyperFrames / Remotion / Manim を呼び分ける上位レイヤ**でもある。
- **HyperFrames**（`heygen-com/hyperframes`）— HTML から動画を作るレンダリングエンジン。

本スタジオでは video-use を工程5（実写編集）、HyperFrames を工程4（モーション）に置き、
両者を Remotion の下流で合流させている。

## データの流れ

すべての工程は `projects/<id>/project.json` という単一のマニフェストを読み書きする。

```
projects/<id>/
├── project.json          ← 唯一の真実。全工程がここを読み書きする
├── timeline.json         ← 工程7 が出力。Remotion の描画計画
├── assets/
│   ├── images/           ← 工程3（GPT Image 2）
│   ├── motion/           ← 工程4（HyperFrames の透過 WebM / Kling の MP4）
│   ├── footage/          ← 工程5（video-use が編集した実写）
│   ├── audio/            ← ナレーション・BGM
│   ├── subtitles/        ← 工程6（master.srt）
│   └── design/           ← Figma 由来の素材
└── out/
    └── final.mp4         ← 工程8
```

`shots[]` が全工程の作業単位になる。工程2 がこれを作り、以降の工程が
それぞれの成果物を `assets[]` に足して `shot.assetIds` で紐づけていく。

## レイヤー順序を固定している理由

合成時のレイヤーは下から `base → overlay → 字幕` で固定してある。

字幕を最上位に置くのは video-use の Hard Rule 1（「字幕はフィルタチェーンの最後に適用する」）
と同じ理由で、オーバーレイに隠れて消えるのを防ぐため。これは好みではなく正しさの問題なので、
`steps/07-compose.ts` と `remotion/src/MainVideo.tsx` の両方で同じ順序を守っている。

なお両者は `buildTimeline()` を共有しているため、工程7 が検証した内容と
実際のレンダリング結果が食い違うことはない。
